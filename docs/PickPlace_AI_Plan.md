# PickPlace AI 개발 계획서

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-10-15 |
| 프로젝트 | AI 기반 지역 상권 진단 서비스 PickPlace |
| 문서 목적 | AI 기능 범위, 데이터 확보 전략, 모델 학습·평가 및 서비스 연동 방향 정리 |
| 문서 상태 | 논의 내용을 정리한 개발 제안안. 실제 데이터 수집·모델 학습·성능 검증 완료를 의미하지 않음 |

## 1. 개발 방향 요약

PickPlace의 AI 기능은 지역과 업종에 따른 상권의 성장 가능성, 위험요인 및 업종 적합도를 분석하고 판단 근거를 제공한다.

첫 MVP는 **성장 예측 모델 1개를 우선 개발하고, 위험도와 업종 적합도는 설명 가능한 진단지표로 계산**하는 방향을 제안한다. 기능별로 학습 모델이 반드시 하나씩 필요한 것은 아니다.

| 제공 기능 | 1차 구현 방향 | 결과 |
|---|---|---|
| 성장 가능성 | 다음 분기의 전년 동기 대비 추정매출 증가율을 예측하는 회귀 모델 | 예상 증가율, 필요 시 성장점수·등급 |
| 상권 위험도 | 매출 감소, 폐업률, 경쟁 과밀 등 확보한 지표를 조합 | 상권 위험지수, 주요 위험요인 |
| 업종 적합도 | 지역 수요·경쟁 수준·안정성 등을 조합 | 업종 적합도 점수, 세부 평가 근거 |
| 판단 근거 | 모델의 변수별 기여도와 지표별 점수 산정 근거 제공 | 긍정·부정 영향 요인, 진단 요약 |

지역 확대는 다음 두 단계로 구분한다.

- **전국 기본진단:** 공통으로 확보할 수 있는 점포·인구·시설 데이터로 수요와 경쟁 수준 등을 제공한다.
- **지역별 성장 예측:** 동일한 기준의 과거 매출 이력을 확보하고 성능을 검증한 지역에 제공한다.

전국 서비스 가능 범위와 실제 데이터 확보 범위는 별도로 관리한다. 전국의 모든 지역에 동일한 예측 기능을 제공한다고 먼저 확정하지 않는다.

모델은 CPU 실행을 기본으로 준비한다. GPU 서버 도입 여부는 실제 학습 시간과 자원 사용량을 확인한 뒤 판단한다. Lightsail에서 사용자 요청을 처리하면서 모델을 재학습하는 구성은 초기 범위에서 제외한다.

## 3. MVP 범위

### 3.1 우선 구현

1. 지역·업종·기준 시점에 맞는 분석 데이터 구성
2. 과거 매출 이력이 확보된 지역의 성장 예측
3. 확보한 지표에 근거한 위험도·적합도 계산
4. 주요 영향 요인과 템플릿 기반 진단 요약
5. 데이터 부족·미지원 지역 처리
6. FastAPI 추론 API와 Spring Boot 연동
7. 기준 모델 비교 및 시간순 성능 평가

### 3.2 후속 확장

| 확장 기능 | 선행 조건 |
|---|---|
| 다른 업종·지역의 성장 예측 | 공통 특징값, 과거 매출 이력 및 지역·업종별 평가 |
| 미래 상권 위험 예측 모델 | 미래 매출 감소·폐업률 상승 등 학습 목표와 이력 확보 |
| 개별 점포 폐업 예측 | 점포별 영업·폐업 이력, 관측기간 및 검증 설계 확보 |
| 상권 유형 군집화 | 유형의 활용 목적과 결과 해석 기준 마련 |
| 유사 지역·업종 추천 | 추천 기준과 실제 추천 성능 평가 방법 마련 |
| 임대료를 반영한 경제성 평가 | 분석 지역과 일치하는 임대료 자료 확보 |
| 생성형 AI 보고서 | 수치와 근거를 유지할 수 있는 생성·검증 절차 마련 |

군집화, 개별 점포 폐업확률, 전국 모든 지역의 매출 예측, 장문 생성형 보고서는 첫 모델의 필수 완료 조건으로 두지 않는다.

### 4.3 확보 순서

1. 전국 상가정보와 주민등록 인구를 확보해 기본진단 범위를 확인한다.
2. 서울의 매출·점포·인구 자료를 동일한 지역·기간 기준으로 연결한다.
3. 카페 한 업종으로 데이터 정제부터 예측 API까지 검증한다.
4. 다른 업종과 지역의 데이터 품질·공통 변수·검증 가능성을 조사한다.
5. 성장 예측 지원 지역을 별도로 등록하고 순차 확대한다.

- 제공기관, 데이터셋명, 공식 URL 및 이용조건
- 다운로드·API 등 확보 방법과 필요한 인증키
- 관측기간, 갱신주기, 실제 공개일 및 수집일
- 행정동·시군구·상권·격자 등 공간 단위
- 업종 분류 체계와 코드 버전
- 매출의 추정·관측 여부, 집계기간 및 금액 단위
- 결측률, 중복률, 비공개·미집계 값의 의미

인증키와 대용량 원본 데이터는 Git에 직접 올리지 않는다. 원본 데이터, 정제 데이터 및 학습 데이터는 구분하고 추출 조건을 남긴다.

## 5. 분석 단위 및 전처리

### 5.1 분석 단위

첫 성장 모델은 **행정동 × 업종 × 분기**를 한 행의 기준으로 제안한다. 여러 행정동의 데이터를 함께 학습하되, 화면에 보여줄 시연 지역은 별도로 제한할 수 있다.

| 필드 | 의미 |
|---|---|
| `region_code` | 공통 행정구역 코드 |
| `region_code_version` | 행정구역·코드 적용 기준 |
| `industry_code` | 공통 업종 코드 |
| `industry_code_version` | 업종 매핑 기준 |
| `period` | 해당 데이터의 관측 분기 |
| `sales_amount` | 정의와 단위를 통일한 추정매출 |
| `store_count` | 같은 범위의 점포 수 |
| `opening_count`, `closing_count` | 제공되는 경우의 개업·폐업 수 |
| `resident_population`, `working_population` | 범위와 기준 시점을 명시한 인구 |
| `floating_population` | 제공되는 경우의 유동인구. 주민등록 인구와 구분 |
| `source_dataset`, `source_version` | 출처 및 데이터 버전 |
| `available_at`, `collected_at` | 사용 가능해진 시점 및 실제 수집 시점 |

행정동 전체 인구처럼 업종 구분이 없는 값은 각 업종 행에 연결할 수 있지만, 업종 행들을 합산해 인구를 중복 집계하지 않는다. 전국 기본진단에는 연간·월간 자료도 사용할 수 있으며, 관측 시점과 집계 방법을 따로 표시한다.

### 5.2 처리 원칙

- 행정동·법정동·SGIS 코드 등을 문자열로 관리하고 공식 대응표·공간 매핑으로 연결한다. 단순 자릿수 절단으로 통일하지 않는다.
- 시군구 자료를 행정동별 실제 관측값처럼 복제하지 않는다. 필요하면 시군구 맥락 변수로 구분한다.
- 행정구역 개편과 업종 분류 변경 전후의 연결 가능성을 확인한다.
- 월별 매출은 정의에 따라 합산하되, 인구 같은 시점별 규모는 분기말 값 또는 평균 등 적절한 기준을 사용한다.
- 연간 자료는 예측 시점에 공개된 최신 연도를 사용한다. 분기별 실제 관측값으로 표현하지 않는다.
- 좌표는 원본 좌표계를 기록하고 지도·공간 분석에 맞게 변환한다.
- 결측, 0, 비공개, 미집계를 구분한다. 매출·점포 수가 없는 값을 일괄 0으로 채우지 않는다.
- 예측 정답인 미래 매출이 없는 행은 지도학습·평가용 라벨에서 제외한다.
- 필수 정보가 부족하면 분석 불가를 반환한다. 선택 변수가 없는 경우에는 해당 변수가 없는 조건으로 검증한 모델·지수만 사용한다.

지역별로 서로 다른 입력을 임의로 대체하기보다 기본진단과 성장 예측의 지원 범위를 나눈다.

## 6. 첫 성장 예측 모델

### 6.1 예측 목표

입력 기준 분기를 `t`, 해당 행정동·업종의 동일 기준 추정매출을 `S(t)`라고 한다. 첫 학습 목표는 다음 분기의 전년 동기 대비 증가율이다.

```text
예측 대상 분기 = t + 1
목표 증가율 y = S(t + 1) / S(t - 3) - 1
```

`t + 1`의 전년 동기는 `t - 3`이다. 예를 들어 2025년 4분기까지의 관측값을 입력하는 표본에서, 목표는 2026년 1분기와 2025년 1분기의 추정매출 비교다. 이 예시는 분기 관계 설명용이며 해당 시점에 모든 입력이 공개되었다는 의미는 아니다.

- `S(t - 3)`가 0이거나 결측이면 해당 증가율 라벨을 제외한다. 작은 분모로 증가율이 과도해지는 경우의 최소 매출 기준은 데이터 분포를 보고 정한다.
- 결과는 행정동·업종 집계의 추정매출 성장률이다. 개별 점포 매출이나 창업 성공률을 의미하지 않는다.
- 추정매출 자체의 오차와 산정 방식 변경도 모델의 한계에 포함한다.
- 총매출은 점포 수 증가의 영향도 받으므로, 점포 수 변화와 함께 해석한다.
- 입력 기준 분기, 실제 분석일, 예측 대상 분기, 비교 기준 분기를 응답에 구분해 담는다.
- 최신 공개 분기의 다음 분기가 분석일 기준 이미 지나갔다면 그 결과를 미래 전망으로 표시하지 않는다. 현재 이후를 예측하려면 공개 지연을 반영한 예측 시차와 재검증이 필요하다.

### 6.2 특징값 후보

초기에는 핵심 특징값 약 10~20개로 시작하고, 검증 결과에 따라 추가한다.

| 영역 | 후보 |
|---|---|
| 매출 추세 | 최근 분기별 매출, 전년 동기 대비 증가율, 최근 4개 분기 평균·변동성 |
| 점포 변화 | 동종업체 수, 점포 수 증가율, 개업·폐업 수 또는 제공기관의 폐업률 |
| 수요 | 주거인구, 직장인구, 유동인구 및 변화율 |
| 경쟁 | 면적 대비 점포 수, 정의를 명시한 인구 대비 점포 수 |
| 계절·지역 | 분기, 업종, 지역 구분 및 확보한 지역 특성 |
| 접근성 | 교통·주요 시설 수 또는 거리. 데이터 확보 후 추가 |

전년 동기 증가율 등 각 특징값에 필요한 과거 길이를 계산해 최소 이력 기준을 정한다. 폐업률의 분모, 유동인구 집계기간, 면적 범위는 특징 정의서에 기록한다.

### 6.3 비교 모델

| 순서 | 후보 | 목적 |
|---|---|---|
| 1 | 전년 동기 매출 유지 | 목표 증가율을 0%로 예측하는 기준 |
| 2 | 최근 전년 동기 증가율 유지 | 현재의 성장 추세를 유지하는 기준 |
| 3 | 선형회귀 또는 규제 선형회귀 | 단순 ML 기준 성능 확인 |
| 4 | LightGBM 회귀 | 비선형 관계를 학습하는 우선 후보 |

LightGBM은 회귀 및 CPU 실행을 지원한다. 최종 선택은 같은 평가 구간에서의 성능, 지역별 오차, 메모리와 추론 시간을 비교해 결정한다. [LightGBM 공식 문서](https://lightgbm.readthedocs.io/en/stable/Parameters.html)

여러 알고리즘의 대규모 탐색보다 첫 모델의 데이터 품질·라벨·평가 조건을 먼저 확정한다. XGBoost·CatBoost 등 추가 비교는 첫 평가 결과가 나온 후 필요할 때 수행한다.

## 7. 위험도 및 업종 적합도

### 7.1 상권 위험지수

첫 버전은 확보한 현재·과거 지표로 지역의 위험 신호를 설명한다.

| 항목 | 위험 신호 예시 |
|---|---|
| 매출 | 지속적인 감소 또는 큰 변동 |
| 수요 | 유동인구·배후인구 감소 |
| 경쟁 | 동종업체 밀집 및 수요 대비 점포 수 증가 |
| 안정성 | 폐업률 상승, 개업 대비 폐업 증가 |

지표 방향을 통일하고 표준화한 뒤 가중 합산하는 방식을 검토한다. 초기 가중치는 제안값으로 구분하고 전문가 검토 및 과거 결과 비교로 보완한다. 현재 지표로 계산한 위험지수와 미래의 위험 예측 결과를 구분한다.

**상권 위험지수는 개별 점포 폐업확률이 아니다.** 점포별 이력과 평가가 없는 상태에서 폐업확률을 제공하지 않는다.

### 7.2 업종 적합도

수요, 경쟁 수준, 안정성 및 검증된 성장 예측이 있는 경우의 성장성을 조합한다. 접근성·임대료는 자료가 확보된 범위에서 추가한다.

적합도는 행정동·업종 수준의 상대 평가다. 개별 건물, 층, 임대 조건까지 평가하는 결과로 표현하지 않는다. 점수가 높다는 이유로 수익이나 창업 성공을 보장하지 않는다.

### 7.3 점수 정의 및 비교 범위

- 0~100점 변환 방법, 등급 경계, 가중치와 비교집단을 문서화한다.
- 같은 업종과 일관된 기준의 지역들끼리 비교한다.
- 기준 분포·점수 정책에 버전을 부여하고 응답에 포함한다.
- 지표가 부족한 기본진단과 상세진단에는 별도 정책을 둔다. 누락 지표의 가중치를 임의 재분배해 같은 점수처럼 비교하지 않는다.
- `예상 성장률`, `성장점수`, `위험지수`, `적합도`를 별도 필드와 라벨로 표시한다.

## 8. 학습 및 평가

### 8.1 시간순 검증

1. 지역과 업종을 합친 전체 표본을 목표 분기 기준으로 구분한다.
2. 과거 목표 분기로 학습하고 이후 분기로 모델을 선택·조정한다.
3. 마지막 일부 목표 분기는 최종 테스트용으로 보존한다.
4. 가능한 범위에서 예측 시점을 이동하며 반복 평가한다.
5. 새로운 지역을 지원할 때는 해당 지역을 제외한 학습 또는 별도 지역 평가도 수행한다.

같은 분기에 속하는 지역 표본들은 같은 시간 구간에 배치한다. 표본 행을 무작위로 나누거나 단순 행 순서로 시간 분할하지 않는다. 시계열 예측에서는 시간 의존성과 평가 방식에 따라 결과가 달라질 수 있다. [scikit-learn 시계열 예제](https://scikit-learn.org/stable/auto_examples/applications/plot_time_series_lagged_features.html)

### 8.2 데이터 누수 방지

- 관측기간과 공개·사용 가능 시점을 구분한다. 예측 실행일 이후에 공개된 입력·라벨은 해당 시점의 학습과 예측에 사용하지 않는다.
- 미래 분기의 매출·폐업·인구를 현재 특징값에 넣지 않는다.
- 특징값의 이동평균·증가율은 해당 시점까지의 값으로 계산한다.
- 결측값 대체, 인코딩, 스케일링 및 변수 선택은 학습 구간에서만 적합한다.
- 모델 튜닝과 점수·등급 결정에 최종 테스트 정답을 사용하지 않는다.
- 과거 공개 버전을 보관하지 않아 최신 수정 자료로 평가하는 경우, 당시의 예측 환경을 완전히 재현하지 못한다는 한계를 기록한다.

전처리를 Pipeline으로 관리하면 학습·검증 처리의 일관성을 유지하고 누수를 줄이는 데 도움이 된다. [scikit-learn 데이터 누수 및 전처리 가이드](https://scikit-learn.org/stable/common_pitfalls.html)

### 8.3 평가 항목

| 항목 | 확인 내용 |
|---|---|
| MAE | 성장률 예측의 평균 절대 오차 |
| RMSE | 큰 오차를 포함한 전체 예측 오차 |
| 기준 모델 비교 | 같은 데이터·구간에서 단순 예측 대비 개선 여부 |
| 지역·업종별 오차 | 평균 성능이 특정 지역의 실패를 숨기지 않는지 |
| 표본 및 기간 | 평가에 포함된 지역, 업종, 분기, 표본 수 |
| 서비스 자원 | 추론 시간, 초기 모델 로딩 시간, 메모리, 동시 요청 시 동작 |

증가율을 비율로 저장하는 경우 `0.05`는 5%를 뜻한다. 성장률 오차를 퍼센트포인트로 표시할 때는 100을 곱해 단위를 명시한다.

수용 가능한 오차와 최소 개선 기준은 실제 기준 모델 결과를 확인하고 최종 테스트 전에 합의한다. 회귀 모델을 일괄적으로 '정확도 95%' 등으로 표현하지 않는다. 기준 모델보다 개선이 없으면 특징값·라벨·데이터를 다시 검토하고, 검증 전 결과를 확정된 예측 성능으로 발표하지 않는다.

### 8.4 타지역 적용

서울 학습 모델의 다른 지역 적용에는 다음 확인이 필요하다.

- 입력 지표의 정의와 업종·공간 범위가 동일한가?
- 서울에서 사용한 특징값을 해당 지역에서도 확보할 수 있는가?
- 매출 산정 방식과 표본·추정 범위가 비교 가능한가?
- 소비 구조와 상권 규모가 달라졌을 때 실제 오차는 어느 정도인가?

값이 없는 지역의 입력을 0으로 채워 그대로 실행하지 않는다. 실제 매출 이력이 부족해 성능을 검증하지 못한 지역에는 기본진단을 우선 제공한다.

## 9. 판단 근거와 데이터 신뢰성 표시

| 결과 | 설명 방법 |
|---|---|
| 성장 예측 | SHAP 등으로 개별 예측에 기여한 변수 표시 |
| 위험지수·적합도 | 산식에 포함한 항목, 지표 값 및 기여점수 표시 |
| 진단 요약 | 실제 계산 결과를 템플릿에 넣어 문장 생성 |
| 데이터 상태 | 결측 여부, 확보한 과거 기간, 기준 시점 표시 |

전역 Feature Importance와 개별 요청의 영향 요인을 구분한다. SHAP은 모델의 예측에 대한 설명이며 실제 경제적 인과관계를 증명하지 않는다. [SHAP 공식 문서](https://shap.readthedocs.io/en/latest/)

첫 버전은 검증되지 않은 `신뢰도 81%` 같은 숫자 대신 데이터 상태와 모델 평가 오차를 제공한다. 수치형 불확실성은 산출 방법, 검증 구간 및 적용 범위를 마련한 후 추가한다.

데이터가 부족한 경우 다음과 같이 표시한다.

- 과거 매출 이력 부족: 성장 예측 미제공, 기본진단 유지
- 필수 지표 누락: 해당 지수 미산출
- 검증되지 않은 지역·업종: 성장 예측 지원 범위 밖으로 표시
- 데이터 기준 시점 불일치: 사용 시점과 제한사항 표시

## 10. 학습·서비스 연동 및 배포

### 10.1 구조

```text
[로컬 PC 또는 Colab]
데이터 확인 → 공통 특징 생성 → 모델 학습·평가
                              ↓
                  모델·전처리·메타데이터 저장
                              ↓ 버전별 배포
[AWS Lightsail]
사용자 브라우저 → Nginx → Spring Boot
                            ├─ PostgreSQL/PostGIS: 상권 데이터 조회
                            └─ Docker AI 서비스
                                 └─ FastAPI
                                      ├─ 공통 특징 생성·전처리
                                      ├─ 성장 예측 모델
                                      ├─ 위험도·적합도 계산
                                      └─ 영향 요인·요약 생성

응답: FastAPI → Spring Boot → Nginx → 사용자 브라우저
```

FastAPI와 모델은 같은 컨테이너에서 실행한다. 초기 구조에는 별도 Lambda·Cloud Run 추론 서버를 추가하지 않는다. 자원 격리가 필요해지면 FastAPI·모델 컨테이너를 함께 별도 환경으로 옮길 수 있도록 호출 계약을 유지한다.

### 10.2 파트별 책임

| 담당 | 책임 |
|---|---|
| BE | 원천 데이터 수집·DB 적재, 코드·기간 정합성 관리, 요청에 필요한 집계·이력 조회, AI API 호출, 통계·AI 결과 통합 |
| AI | 분석 단위·라벨·특징값 정의, 학습과 추론의 공통 계산 코드, 모델 학습·평가, 지수 정책, FastAPI, 모델 버전·입력 검증 |
| FE | 점수·성장률·영향 요인 시각화, 기준 시점 표시, 분석 가능·불가 및 오류 상태 구분 |
| 공동 | 데이터 정의서, API 계약, 지원 지역·업종, 변경 및 배포 기준 합의 |

권장 요청 방식은 BE가 공통 형식의 집계·과거 이력을 전달하고 AI가 같은 특징 생성 코드로 모델 입력을 계산하는 것이다. BE가 이미 계산한 특징값을 전달하는 방식을 선택할 경우에도 AI가 관리하는 동일한 정의와 계산 기준을 검증해 사용한다. 파트별로 같은 증가율을 서로 다른 방식으로 구현하지 않는다.

### 10.3 내부 API 초안

| API | 역할 |
|---|---|
| `GET /health` | 서비스 준비 상태 및 필수 모델 로딩 확인 |
| `GET /model-info` | 모델·특징 스키마·점수 정책 버전과 지원 범위 확인 |
| `POST /predict` | 집계·이력을 받아 가능한 예측·지수·근거를 반환 |

실제 요청·응답 형식은 BE·AI 합의 후 확정한다. 최소 계약은 다음과 같다.

| 구분 | 필수 정의 |
|---|---|
| 요청 식별 | 지역·업종 코드, 코드 버전, 입력 스키마 버전 |
| 시간 | 분석 실행일, 각 입력의 관측기간·공개 시점, 예측 기준 분기 |
| 데이터 | 매출·점포·인구 집계 및 특징값 계산에 필요한 이력 |
| 성장 결과 | 제공 상태, 목표 분기, 전년 비교 분기, 예상 증가율, 모델 버전 |
| 지수 결과 | 제공 상태, 점수·등급, 산식·정책 버전 |
| 근거 | 변수명·지표명, 영향 방향, 기여값의 단위 |
| 품질 | 데이터 상태, 누락 항목, 사용한 데이터 기준 시점 |
| 분석 불가 | 값은 `null`, 원인은 `insufficient_history`·`unsupported_region` 등 명시 |

전체 성공·실패만 반환하기보다 성장 예측과 각 지수의 제공 상태를 따로 관리한다. AI 호출이 실패해도 Spring Boot는 기본 통계를 제공하고 AI 분석 불가 상태를 전달한다. 누락·실패를 0점으로 표시하지 않는다.

### 10.4 운영 원칙

- FastAPI 시작 시 모델과 전처리 객체를 한 번 로딩한다.
- 초기 worker는 1개로 시작하고, 병렬화에 따른 모델 메모리 중복을 측정한다.
- 모델 스레드 수와 동시 요청 수를 제한해 Spring Boot·DB와의 자원 경쟁을 확인한다.
- 정상 요청, 초기 로딩, 동시 요청의 응답 시간과 메모리 사용량을 측정한다.
- AI API는 내부 네트워크에서 호출하고 외부에 직접 공개하지 않는다.
- BE에서 타임아웃을 설정한다. 반복 호출·캐시는 모델 버전, 점수 정책, 데이터 버전을 키에 포함한다.
- 모델·전처리·특징 스키마·점수 정책을 호환되는 한 묶음으로 배포하고 이전 버전을 보관한다.
- 학습·추론의 Python 및 라이브러리 버전을 고정한다. 신뢰할 수 있는 팀 산출물만 로딩한다. [모델 저장·환경 호환성 가이드](https://scikit-learn.org/stable/model_persistence.html)
- 모델 파일과 대용량 데이터는 별도 산출물 저장소에서 관리하고 배포 시 주입하거나 이미지에 포함한다. Git에는 코드·설정·스키마·평가 문서와 산출물 식별 정보를 남긴다.
- 코드 배포 후 매번 재학습하지 않는다. 새 데이터 적재와 모델 재학습·검증·배포는 별도 작업으로 관리한다.
